## 附录 B　口径统一说明

原始需求存在若干表述省略或与实际环境不一致之处，经确认后统一如下，便于审计追溯：

| 原始需求原文 | 歧义点 | 本规范口径 | 确认方式 |
|---|---|---|---|
| 第 3 条“前端 dist 应在 `/frontend`，后端因在 `/backend`” | 指交付包内还是容器内 | **交付包内** `frontend/dist/`、`backend/`；**容器内** 前端 `/frontend`、后端 `/app` | 用户确认以原始需求为准 |
| 第 3 条“后端应将 `/` 路径静态解析至 `/frontend`” | 与“项目自带 nginx 托管静态”的常见做法冲突 | **以原始需求为准**：FastAPI 监听 80 并托管静态，项目内不设 nginx 容器 | 用户确认（架构选型） |
| 第 3 条“`api` 路径规范至 `/api/v1/xxx/xxx`” | 未给命名细则 | [§4.6](04-端口路径与网关接入.md) 明确“`/模块/功能`”结构 + 强制 `/api/v1/health` | 规范细化 |
| 第 4 条 `.env.exsample` | 拼写疑似笔误 | **修正为 `.env.example`** | 用户确认为笔误 |
| 第 5 条“对外映射文件夹仅限三类” | 未列具体目录名 | 固定 `conf/`、`uploads/`、`downloads/` | 用户确认由规范定义 |
| 第 6 条“`DB_HOST` 使用 `mariadb`、`pgsql`” | pgsql 是否存在 | 两者均允许，**pgsql 待运维部署**；基准环境当前仅启用 `mariadb:10.11` | 用户确认 |
| 第 6 条“配置尽量放 `.env`” | “尽量”不明确 | 升级为**强制**：可变配置一律入 `.env` | 规范收紧 |
| 第 7 条“项目放置于 `/home/docker/项目名`” | 既有部署路径可能与本条不一致 | **以原始需求为准**：统一部署在 `/home/docker/<项目名>/`（见 [§3.4](03-强制条款.md)） | 用户确认 |
| 第 7 条“`linux vm 虚拟机`” | 未给版本基线 | [§2.2](02-目标架构.md) 记录基准环境（Docker 28.5.2 / Compose v2.35.1 等），并明确目标架构为 x86_64 | 实测补充 |

## 附录 C　原始需求原文归档

原始需求原为工作区根目录的 `readme.txt`（现已移除），**原文完整归档于此**，作为规范编写依据与后续修订的比对基线。

```text
适用范围：此规范适用于在互联网开发BS架构的系统，遵从此规范可以无缝将外部开发的应用向内网服务器迁移。
必要条件：linux vm虚拟机
架构规范(推荐)：推荐使用python fastapi做后端，vue或react等框架做前端。前端dist应在/frontend，后端因在/backend。后端应将/ 路径静态解析致/frontend 文件夹,api路径应规范致/api/v1/xxx/xxx,按照/模块/功能定义api路径。
交付物(强制)：docker包、docker-compose.yml、init.sh、update.sh、.env.exsample
docker规范：所有环境依赖及代码都应放置于docker包内、对外映射的文件夹仅限于配置文件、用户上传文件、供用户下载的文件。docker内部应只提供 0.0.0.0:80的服务
docker-compose.yml规范：应加入 gateway-network，所有的配置应尽量放置在.env文件中。数据库DB_HOST 使用 mariadb、pgsql(数据库作为基础服务已经以docker形式部署在虚拟机中)
linux vm 虚拟机部署规范：项目应放置于 /home/docker/项目名。
```
