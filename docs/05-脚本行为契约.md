# 5. `init.sh` / `update.sh` 行为契约

> 内网 B/S 架构开发规范 v2.5 · 第 5 章 ｜ [返回总览](../readme.md) ｜ 上一章：[§4 端口、路径与网关接入](04-端口路径与网关接入.md) ｜ 下一章：[§6 交付与验收](06-交付与验收.md)

两个脚本均为**强制交付物**，必须满足以下契约。脚本只操作当前项目目录，不得触碰宿主的 `conf.d`、共享数据库与其他项目。

**【强制】** 两个脚本必须以 LF 行尾交付，且必须支持 `--dry-run` 与 `--help`。CRLF 会导致直接执行时 shebang 先失效（实测 `env: 'bash\r'`，退出码 **127**）；改用 `bash init.sh` 调用时，脚本内置守卫会给出可操作的修复提示并退出 **1**（该守卫位于 shebang 之后、`set` 之前，并以注释结尾，因此 CRLF 下仍可解析——此写法经实测验证；守卫检查**整个文件**，不是只查开头若干字节）。

**【强制】** CRLF 自检的文件清单是**唯一**的（[§3.1](03-强制条款.md) / [§6.2](06-交付与验收.md) / [`templates/README.md`](../templates/README.md) 均以本节为准）：交付前查 `init.sh update.sh .env.example`，内网生成 `.env` 后追加查 `.env`。自检与修复：

```bash
# 交付前（.env 尚未生成）
grep -c $'\r' init.sh update.sh .env.example   # 期望全部为 0
sed -i 's/\r$//' init.sh update.sh .env.example

# 内网 cp .env.example .env 之后
grep -c $'\r' .env                             # 期望为 0
sed -i 's/\r$//' .env
```

> 根治办法：把 `.gitattributes` 一并放进交付包（`*.sh` / `*.env*` / `*.conf` / `*.sql` 锁定 `eol=lf`），并**在 Linux（WSL/容器）里打交付包**，避免 Windows 侧再次引入 CRLF 与丢失 exec 位。

## 5.1 `init.sh`（首次部署）

| 项 | 契约 |
|---|---|
| 前置 | 脚本所在目录即项目根目录；`.env` 必须已由人工从 `.env.example` 复制并填写 |
| 权限 | 需要 root 或可用的 `sudo docker`；脚本自行探测并使用（实测部署用户不在 docker 组） |
| 幂等 | 重复执行必须安全：目录创建幂等、镜像已存在可重复 `load`、`compose up -d` 幂等 |
| 预检 | 逐项校验并给出可操作提示：docker / compose 可用、`gateway-network` 存在、宿主 80 端口未被非网关进程占用、`.env` 关键键齐全、**未残留 `.env.example` 占位值**、脚本为 LF 行尾 |
| 密钥 | `SECRET_KEY` 缺失、仍为占位值或不足 32 字符时，脚本用 `openssl rand -hex 32` 生成并**写回 `.env`**（幂等，只在需要时写一次）；现场无需手工填写 |
| 目录 | 创建 `conf/ uploads/ downloads/ backups/`，并设定属主与权限（`conf/ uploads/ downloads/` → `APP_UID:APP_GID`） |
| 建库（可选） | `DB_PROVISION=auto` 时自动按 `.env` 的 `DB_DATABASE` / `DB_USERNAME` 建库建号，并随机生成 `DB_PASSWORD` 写回 `.env`（幂等）；**root 口令绝不进命令行**，按 `DB_ROOT_PASSWORD_FILE` → 环境变量 → 常见编排文件顺序探测，找不到则回退人工并打印可复制命令 |
| 镜像 | 导入目录内 `*.tar`（`docker load`）；省略 `--tar` 时按修改时间取**最新**的一个，目录内多于一个时告警，避免旧包覆盖新包 |
| 启动 | `docker compose up -d --remove-orphans` |
| 自检 | 轮询健康检查至 `healthy`（默认 120s），成功后打印验收命令与网关投放指引 |
| 退出码 | `0` 成功；`1` 预检失败；`2` 启动后健康检查失败（保留现场，不自动回滚）；`127` 解释器不可用（脚本为 CRLF 行尾） |
| 其他 | 支持 `--tar <文件>`、`--dry-run`（只打印动作）与 `--help`；全过程带时间戳日志；失败即 `exit` 非 0 |

## 5.2 `update.sh`（版本更新）

【强制】行为序列固定为：**自动备份 → 导入新镜像 → 重建容器 → 健康校验 → 失败自动回滚并告警**。

| 项 | 契约 |
|---|---|
| 用法 | `./update.sh [--tar <项目名>-app.tar] [--keep N] [--allow-same-image] [--no-rollback] [--dry-run]`；`--tar` 省略时取项目根目录下最新的 `*.tar` |
| 备份 | 创建**时间戳快照目录** `backups/<时间戳>/`，内含 `.env`、`docker-compose.yml`、`docker save` 出的镜像包与 `MANIFEST`（当前镜像不存在时跳过镜像备份并记录） |
| 镜像校验 | 导入后比对镜像 ID，与更新前相同即中止（退出码 `1`），避免「更新成功但仍跑旧版本」；确需重放同一版本时显式加 `--allow-same-image` |
| 数据库迁移 | 迁移文件放 `deploy/migrations/NNNN_描述.sql`，**按文件名字典序执行**，已执行版本记录在库内 `schema_migrations` 表。**推荐由应用启动时自动前滚**——此时 `.dockerignore` 不得排除 `deploy/`，且 `Dockerfile` 必须 `COPY deploy/migrations /app/migrations`（否则镜像里没有迁移文件，首次部署会因表不存在而失败）；也可提供 `migrate.sh` 由运维执行。**三条硬规则**：① **已发布的迁移文件不得修改**——别人的库已执行过，改了不会重跑，只会让新旧环境结构不一致，要改就新增 `0002_*.sql`；② **必须前后兼容（expand-contract）**：新增列先发布迁移、下个版本代码再用，删除列先让代码停用、隔一个版本再删——因为回滚只回镜像、**不回数据库**；③ **只用三方言都认识的语法**（见 [§3.6](03-强制条款.md)） |
| 更新 | `docker load -i <tar>` → `docker compose up -d --force-recreate`；重建后若容器 IP 变化会打印网关 reload 提示（见 [§4.2](04-端口路径与网关接入.md)） |
| 校验 | 轮询健康检查至 `healthy`（默认 120s） |
| 回滚 | 健康检查失败时：`docker load` 回快照镜像 → **还原快照中的 `docker-compose.yml`** → `up -d --force-recreate` → 再次校验；**无论回滚是否成功都必须告警**（打印醒目错误；若 `.env` 中配置了 `ALERT_WEBHOOK` 则 POST 该地址）。`.env` **不自动还原**，只打印手工回退命令 |
| 归档 | 保留最近 `--keep`（默认 5）个**快照目录**（`--keep 0` 表示全部删除，之后无法自动回滚），并清理本次被替换掉的旧镜像（防悬空镜像累积）；旧版平铺备份不会被自动清理，脚本会提示 |
| 并发 | 使用 `flock` 加锁，防止两次更新并发 |
| 退出码 | `0` 成功；`1` 预检失败；`2` 已回滚（服务恢复旧版本）；`3` 更新失败且回滚亦失败（需人工介入）；`127` 解释器不可用（脚本为 CRLF 行尾） |
| 其他 | 支持 `--dry-run` 与 `--help`；每步输出带时间戳日志；任何失败不得静默 |

**【强制】** `--no-rollback` 仅供排障使用，常规升级禁止使用。

模板：[`templates/update.sh`](../templates/update.sh)
